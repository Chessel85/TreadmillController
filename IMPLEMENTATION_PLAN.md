## Phase 2 — Manual mode logging (primary objective — build this before Strava/planned mode)
Goal: deliver the PDD's stated primary objective end-to-end, independent of whether Phase 0.1 turns out favorably.

- [x] **2.1 Session state machine.** Start / pause / resume / finish for manual sessions (PDD Ref #3, #6, #7). No treadmill control involved.
- [x] **2.2 Telemetry capture.** If Phase 0.1 found readable BLE characteristics, subscribe and log speed/incline changes with timestamps as they occur (PDD Ref #5). If not readable, fall back to duration-only logging.

## Phase 3 — Strava integration
Goal: get a finished manual session onto Strava — this alone satisfies the PDD's primary objective.

**Revised 2026-08-08** (see Session Log): Strava's API now requires an active paid Strava subscription ($11.99/mo, no free tier, applies to single-user personal apps too) for Standard-tier API access. OAuth auto-upload is dropped on cost grounds. Revised approach: generate a `.tcx` file client-side from the finished session and let the user upload it manually via Strava's free "Upload Activity" page — no API registration, no OAuth, no ongoing cost. Confirmed viable: user tested Strava's manual file-upload page in Firefox + NVDA and reported it's accessible.

- **2026-08-08**: Completed 0.1 via LightBlue scan (screenshots in `docs/ble-screenshots/`, write-up in `docs/ble-findings.md`). Treadmill advertises as `iConsole+0168`. Two relevant services: proprietary `0xFFF0` (notify `0xFFF1` + write `0xFFF2` — the iConsole protocol, undocumented but a known/previously-reverse-engineered pattern) and standard FTMS `0x1826` (read/notify only — no Control Point, so telemetry-only via `0x2ACD` Treadmill Data, but that's the officially documented format so easy to decode). Net result: writable control exists, so Phase 4 auto-control stays in scope, but will need the proprietary `0xFFF2` command format rather than standard FTMS control — research existing open-source iConsole reverse-engineering before attempting from scratch. A separate OTA/DFU service was also found and should be left alone (firmware-flashing, not control).

- **2026-08-08**: Wrote 2.2's telemetry capture. `subscribeToTelemetry()` runs right after `gatt.connect()` succeeds (independent of session state, so a reading is available the instant Start is pressed): gets the FTMS service, gets the `0x2ACD` Treadmill Data characteristic, `startNotifications()`, and listens for `characteristicvaluechanged`. Subscription failure is caught and non-fatal — `telemetryAvailable` stays `false` and the app falls back to duration-only logging, per PDD Ref #5's explicit fallback clause. `decodeTreadmillData()` implements the relevant slice of the Bluetooth SIG FTMS spec by hand (flags bitmask → Instantaneous Speed, walking past Average Speed/Total Distance by their spec-defined byte widths when their flag bits are set, then Inclination) since no library is in use — only Speed and Inclination are extracted; nothing else in the payload is needed yet. While a session is `running`, each notification is compared against the last *logged* reading and only pushed to `sessionLog` (with the current elapsed-time timestamp) if speed or incline actually changed, per Ref #5's "capturing ... as they change" framing rather than a dense continuous sample. A small non-`aria-live` `telemetryDisplay` div shows the current speed/incline for sighted/debugging visibility — deliberately not announced automatically, to avoid interrupting VoiceOver on every notification. Finish's status message now reports the telemetry point count when available. Not yet tested on-device — the FTMS decode logic in particular needs real-world verification since `ble-findings.md` only confirmed the characteristic exists, not its actual flags/payload in practice. This version is **Chimera**.

- **2026-08-08**: Wrote 2.3's local session storage. `saveSessionToStorage()` writes `{mode, state, elapsedSeconds, sessionLog, savedAt}` to `localStorage` under a single `treadmillSession` key — called on every telemetry-driven log push, every timer tick (so `elapsedSeconds` stays current even if nothing else changes), on pause/resume, and on finish. Deliberately independent of the in-memory UI teardown in `onDisconnected`/`resetModeSelection`, so a dropped BLE connection mid-session leaves the last-saved snapshot intact in storage even though the on-screen UI resets to "Not connected" (full reconnect-and-resume UX is still Phase 5.2 — this task is only "don't lose the data"). On page load, `checkForSavedSession()` looks for a saved session and, if found, shows a `role="status"` summary (mode, duration, point count) plus a "Discard saved session" button, since there's no session-history viewer or Strava upload yet for it to feed into — it just needs to be visible and dismissable rather than silently sitting in storage forever. Starting a new session (`startButton` click) calls `clearSavedSession()` first, since the new session immediately begins writing its own data under the same key. Not yet tested on-device — needs a real check that reloading mid-session (or letting the treadmill/Bluefy disconnect) actually leaves recoverable data in `localStorage` and that the recovered-session notice reads correctly.
