## Phase 1 — Accessible shell & Bluetooth connect flow
Goal: the skeleton every other feature sits inside.

- [x] **1.1 Page shell & mode selection.** Semantic, VoiceOver-friendly landing screen: connect-to-treadmill entry point, then choice of Manual vs Planned mode (locked once a session starts, per PDD Ref #2).
- [x] **1.2 Treadmill connect flow.** `navigator.bluetooth.requestDevice` flow with an accessible "scanning / found / connected / failed" state sequence (PDD Ref #1). Verified on the real JTX Sprint 6 in Bluefy (Kraken build).

## Phase 2 — Manual mode logging (primary objective — build this before Strava/planned mode)
Goal: deliver the PDD's stated primary objective end-to-end, independent of whether Phase 0.1 turns out favorably.

- [x] **2.1 Session state machine.** Start / pause / resume / finish for manual sessions (PDD Ref #3, #6, #7). No treadmill control involved.
- [x] **2.2 Telemetry capture.** If Phase 0.1 found readable BLE characteristics, subscribe and log speed/incline changes with timestamps as they occur (PDD Ref #5). If not readable, fall back to duration-only logging.
- [x] **2.3 Local session storage.** Persist the in-progress and completed session log (e.g. `localStorage`/IndexedDB) so a dropped connection or accidental reload doesn't lose data.

## Phase 3 — Strava integration
Goal: get a finished manual session onto Strava — this alone satisfies the PDD's primary objective.

**Revised 2026-08-08** (see Session Log): Strava's API now requires an active paid Strava subscription ($11.99/mo, no free tier, applies to single-user personal apps too) for Standard-tier API access. OAuth auto-upload is dropped on cost grounds. Revised approach: generate a `.tcx` file client-side from the finished session and let the user upload it manually via Strava's free "Upload Activity" page — no API registration, no OAuth, no ongoing cost. Confirmed viable: user tested Strava's manual file-upload page in Firefox + NVDA and reported it's accessible.

- [x] **3.1 TCX generation.** Convert a completed manual session's `sessionLog` into a valid TCX file (absolute timestamps from session start + elapsed offsets; cumulative distance integrated from each segment's held speed × duration, per PDD Ref #5's "time and distance" minimum).
- [x] **3.2 Get the file off the phone.** A "Share / download session file" button shown after Finish: tries the Web Share API (`navigator.share` with a `File`) first, so iOS's native Share Sheet (Mail, AirDrop, Save to Files, etc.) opens directly with the file attached; falls back to a plain browser download if Bluefy doesn't support file sharing. User then uploads the file to Strava themselves (tested working with NVDA + Firefox on the user's PC).
- ~~**3.3 Re-auth/token refresh.**~~ No longer applicable — the revised approach uses no authentication at all.

## Phase 4 — Planned mode (contingent on Phase 0.1 findings)
Goal: PDD Ref #4 and #8. **Before starting, revisit Phase 0.1's findings and choose a direction:**
- If writable BLE control exists → build full auto-control as scoped.
- If only readable/no BLE control exists → redefine this phase as a "plan cueing" feature instead (app announces upcoming speed/incline changes via VoiceOver, user adjusts manually) and update this plan + the PDD to reflect the reduced scope.

- [x] **4.1 Plan file format + parser.** Format finalized from the user's draft at `rp1.txt`: full-line `#` comments; `incline:X% Speed:Ykmh Duration:Z` steps where incline is an integer 0–15, speed is a decimal to 1 place 0.0–20.0, and duration is `Nmin`, `Nsec`, or `NminMsec` (minutes 0–180, seconds 0–59, at least one part, minutes-then-seconds order only); `StartLoop:N` / `EndLoop` repeat blocks (nesting supported). Implemented as `parsePlanFile()` in `index.html` — all-or-nothing validation with line-numbered errors. A minimal file-input UI (not the full 4.2 picker) was added so it's testable on-device: choosing a `.txt` file in Planned mode parses it immediately and shows a loaded-plan summary or the error list.
- [ ] **4.2 Plan upload/selection UI.** Upload a plan file from the user's PC; list previously used plans (PDD Ref #4). Implemented: `rememberPlan()` saves up to 5 most-recently-used plans (filename + text + summary) to `localStorage`; a "Previously used plans" list of one-tap load buttons appears above the upload field when any exist, capped at 5 to minimize VoiceOver scrolling. A stored plan that fails to reparse (e.g. after a future parser change) is dropped automatically rather than left as a dead entry.
- [ ] **4.3 Drive or cue the session** per the direction chosen above.
- [ ] **4.4 UI/UX tidy-up pass.** Review button labeling/wording (e.g. the "Discard saved session" button) and improve the layout/grouping of buttons, labels, and counters across the page — several conditionally-shown elements have accumulated across Phases 1–3 without a cohesive visual pass.

## Phase 5 — Reliability & polish
- [ ] **5.1 Screen wake-lock + user messaging.** Request a wake lock during active sessions; clearly communicate (VoiceOver-friendly) that the phone must stay unlocked and Bluefy foregrounded for the session to keep logging (screen-lock kills the BLE session — confirmed during feasibility research).
- [ ] **5.2 Connection-loss recovery.** Handle a dropped BLE connection or accidental page reload mid-session without losing logged data.
- [ ] **5.3 Full VoiceOver pass.** Walk every screen end-to-end with VoiceOver on-device.
- [ ] **5.4 Real-session sanity check with Spotify.** Run a real session with Spotify streaming to Bluetooth headphones throughout, confirming no interference (expected to just work per feasibility research — this is a verification task, not a build task).

## Session Log
*(Condensed 2026-08-08 — see git history for the full blow-by-blow if needed.)*

- **Pre-plan feasibility review**: (a) JTX Sprint 6 BLE writable-control was unverified upfront — gated Phase 4 on 0.1; (b) iOS drops/throttles BLE on screen-lock/backgrounding — hence Phase 5.1; (c) Strava's client_secret couldn't be hidden in a static site — moot now, see the Phase 3 pivot below; (d) Bluefy is the only Web Bluetooth path on iOS; (e) simultaneous Spotify + treadmill BLE is sound — PDD Ref #10.
- **Phase 0 (complete)**: 0.1 — LightBlue scan found the treadmill (`iConsole+0168`) exposes proprietary `0xFFF0`/`0xFFF1`/`0xFFF2` (notify+write — the real control channel, undocumented iConsole protocol) and standard FTMS `0x1826`/`0x2ACD` (read/notify telemetry only, officially documented). Writable control exists, so Phase 4 auto-control stays in scope (will need the proprietary write format, not standard FTMS control). 0.2 — confirmed via an existing Wahoo KICKR Bluefy+VoiceOver page (`docs/reference/wahoo-kickr-example.html`) that the connect/device-picker flow works with no VoiceOver friction; also a strong pattern reference for later phases (plan-file format, session/timer UI). 0.3 — GitHub Pages live at https://chessel85.github.io/TreadmillController/.
- **Phase 1 (complete)**: Built the accessible shell (connect button, mode radios locked until connected) and the BLE connect flow. Real-device debugging found two issues, fixed together: Bluefy's Web Bluetooth polyfill needs full 128-bit UUID strings (not short hex like `0x1826`) in `optionalServices`, and rejects with non-standard error objects (bare error codes, not `DOMException`) — added `describeError()` to surface whatever Bluefy actually throws. Briefly swapped the `namePrefix` filter for `acceptAllDevices` to debug, then restored the filter once the real cause was fixed, since an unfiltered device picker is real VoiceOver-navigation friction (saved as a standing feedback memory — favor narrow/filtered lists everywhere, incl. future Phase 4.2). Established the mythical-creature version-naming convention this phase (saved to memory).
- **Phase 2 (complete)**: 2.1 — manual session state machine (Start/Pause/Resume/Finish), mode locked during a session per Ref #2. 2.2 — subscribes to FTMS `0x2ACD`, hand-decodes the flags-based payload, logs change-only speed/incline entries with elapsed-time timestamps; confirmed accurate against real console adjustments ("39 points recorded"). 2.3 — `saveSessionToStorage()` persists the session to `localStorage` on every change/tick/pause/finish, independent of in-memory UI teardown on disconnect, so a dropped connection doesn't lose data; a page-load check surfaces a recovered-session summary + discard button. Confirmed on-device: reload mid-session correctly recovered elapsed time and telemetry point count.
- **Phase 3 (core flow complete)**: Attempted OAuth registration but found Strava's API now requires an active paid subscription ($11.99/mo, no free tier, applies to personal single-user apps too) effective June 2026 — see the `project_strava_paywall_pivot` memory. Pivoted to no OAuth at all: `buildSessionTcx()` generates a minimal Garmin TCX v2 file from the session (absolute timestamps from `sessionStartTime` + elapsed offsets; distance integrated segment-by-segment from each held speed value, since `sessionLog` only records changes). A "Share / download session file" button (`shareOrDownloadSessionFile()`) tries the Web Share API with a `File` first — opens iOS's Share Sheet with the file attached — falling back to a plain download if unsupported. Confirmed on-device: Share Sheet opens, file attaches correctly to Mail, user uploads manually via Strava's own free "Upload Activity" page (also confirmed accessible with NVDA + Firefox). Added `title`/`text` to the share call so Mail could prefill subject/body — in practice Mail used the body (with the upload URL) but not the subject line; not a spec-guaranteed field, so that's expected/acceptable. PDD Ref #9 and this plan's Phase 3 section were updated to match the revised, auth-free approach.
- **TCX trackpoint frequency (2026-08-08)**: user asked about file size/limits for a 90–100 min training run. Confirmed there's no fixed sampling interval — points are added only on speed/incline change, so file size scales with how many adjustments a session has, not its duration; no practical size/count limit expected. Flagged that Phase 5.1 (screen wake-lock) isn't built yet, so a long run risks a mid-session BLE drop if the screen locks — 2.3's storage means data up to the drop wouldn't be lost, but the session would end early. User is training for a half marathon and doing 90–100 min sessions, so this is a real near-term consideration, not hypothetical.
- **Plan file format + parser (2026-08-08, Sphinx build)**: user finalized the `rp1.txt` spec (incline 0–15 integer, speed 0.0–20.0 one decimal place, duration as minutes and/or seconds with a 180 min / 59 sec cap, `StartLoop:N`/`EndLoop` blocks) and switched `.gitignore` to stop excluding `*.txt` so real plan files can be committed (pushing those separately themselves). Built `parsePlanFile()`: all-or-nothing validation, line-numbered errors, nested-loop expansion into a flat step list. Wired up a minimal file-input in Planned mode so a chosen `.txt` file is parsed immediately and shows a summary (step count + total duration) or the error list via the status region. Confirmed on-device: user loaded a plan file from their iCloud folder successfully. Not yet used to drive anything — that's 4.3.
- **Plan library (2026-08-08, Pegasus build)**: added a "Previously used plans" list in Planned mode — successfully-parsed plans are saved to `localStorage` (filename, raw text, step count, total duration), capped at the 5 most recently used, with one-tap reload buttons shown above the file upload field. Refactored the upload path and the library-reload path to share `applyPlanParseResult()` so summary/error handling isn't duplicated. Not yet tested on-device.
